# RecruitMatch Copilot 设计规格

日期：2026-08-19

## 1. 目标

将现有通用 RAG 问答 Demo 改造成面向企业招聘团队的多岗位智能推荐平台。招聘人员上传候选人简历后，系统从企业岗位库中推荐最匹配的三个岗位，展示硬性条件、分维度评分、简历原文证据、缺失信息和风险提示，并允许招聘人员确认或纠正推荐。

系统只提供岗位适配建议，不做自动录用或淘汰决定。性别、年龄、民族、照片、婚育等敏感属性不得参与匹配。

## 2. 成功标准

- 支持至少 10 类技术岗位和 30 个不同级别的岗位模板。
- 支持至少 150 份合成简历，以及不少于 300 个经人工复核的简历—岗位标签。
- 固定测试集上的 Top-3 Recall 不低于 85%。
- 硬性条件识别准确率不低于 90%。
- 推荐结果的证据覆盖率不低于 95%。
- 跨租户数据隔离集成测试全部通过。
- 关键业务模块测试覆盖率不低于 80%。
- 所有对外宣称的效果和性能数字均由仓库内可重复脚本生成。

## 3. 用户与权限

### 3.1 企业管理员

- 创建、停用和管理企业成员。
- 分配管理员、招聘人员、招聘负责人角色。
- 查看企业级审计记录和使用量。

### 3.2 招聘人员

- 管理岗位及岗位版本。
- 上传、查看和删除候选人简历。
- 发起岗位推荐，查看证据并提交反馈。

### 3.3 招聘负责人

- 拥有招聘人员的只读或复核能力。
- 查看推荐质量、反馈、成本和处理时延指标。

第一期不提供候选人门户。

## 4. 核心业务流程

1. 管理员创建企业并邀请招聘团队成员。
2. 招聘人员从预置模板创建岗位，或编写自定义 JD。
3. 系统把 JD 解析为岗位画像：岗位族、级别、必备技能、加分技能、经验要求和评分权重。
4. 招聘人员上传 PDF、DOCX 或 TXT 简历。
5. 异步任务校验文件、提取文本并生成候选人结构化画像。
6. 系统先执行硬性条件和岗位族过滤，再召回候选岗位。
7. 匹配引擎对候选岗位执行规则评分、语义评分和证据校验。
8. 系统返回 Top 3，包含总分、维度分、满足项、缺失项、不确定项、证据和风险提示。
9. 招聘人员确认、驳回或改选岗位，并记录原因。
10. 评测和运营模块聚合反馈、失败样本、费用与延迟，支持后续版本回归。

## 5. 范围

### 5.1 第一期必须交付

- 多租户企业空间、JWT 登录和基于角色的访问控制。
- 预置岗位模板，以及企业自定义岗位的增删改查、复制、启停和版本管理。
- PDF、DOCX、TXT 简历上传、校验、解析、结构化和状态查询。
- 多岗位 Top 3 推荐、分维度评分、原文证据和不确定性提示。
- 招聘人员确认、驳回、改选和文字反馈。
- 模型调用、Token、费用、延迟、错误与 Prompt 版本记录。
- 合成数据、离线评测、AI 回归测试、接口测试和租户隔离测试。
- Docker Compose 本地环境、数据库迁移和 CI 流水线。

### 5.2 明确不做

- 自动录用、淘汰、薪资决定或候选人排名决策。
- 完整 ATS、面试排期、Offer、入职或薪酬模块。
- 自动联系候选人。
- 多 Agent、模型微调、知识图谱、Kubernetes 或微服务拆分。
- 未经可重复实验验证的生产规模或业务收益声明。

## 6. 总体架构

采用模块化单体。单个 FastAPI 服务承载 API 和业务模块；耗时的简历解析与匹配任务通过任务队列执行。模块通过服务接口和仓储接口解耦，后续可单独拆分，但第一期不为拆分付出分布式复杂度。

```text
Web UI
  |
FastAPI API
  |-- Identity & Tenant
  |-- Job Catalog
  |-- Resume Intake
  |-- Matching
  |-- Feedback
  |-- Evaluation & Operations
  |
  |-- PostgreSQL + pgvector
  |-- Redis task queue/cache
  |-- S3-compatible object storage
  `-- OpenAI-compatible LLM/Embedding provider

Background Worker
  |-- file extraction
  |-- structured resume/JD parsing
  |-- embedding
  `-- match execution
```

开发与测试环境允许使用 SQLite、内存队列和本地文件存储，生产配置使用 PostgreSQL、Redis 和 S3 兼容对象存储。领域服务不得直接依赖具体基础设施实现。

## 7. 模块边界

### 7.1 Identity & Tenant

负责企业、用户、密码、JWT、角色和租户上下文。所有企业数据表都必须包含 `tenant_id`；仓储查询必须显式接收租户上下文。禁止通过前端传入的 tenant ID 越权切换企业。

### 7.2 Job Catalog

负责岗位模板、企业岗位和不可变岗位版本。一个岗位的每次发布都会生成版本；历史匹配结果引用具体版本，后续编辑不改变历史结果。

岗位画像包含：岗位族、岗位级别、职责、必备技能、加分技能、最低经验、学历限制、语言、地点、能力维度、权重和排除条件。

### 7.3 Resume Intake

负责文件校验、存储、文本提取、候选人画像生成和处理状态。原文件、文本和结构化画像分别保存。解析失败可重试，重复上传通过租户内文件哈希实现幂等。

候选人画像包含：工作经历、项目经历、教育经历、技能、证书、语言和原文证据位置。敏感字段可以识别用于脱敏，但不得写入匹配输入。

### 7.4 Matching

匹配分为四步：

1. 规则过滤：岗位状态、岗位族、必备证书和明确的经验下限。
2. 候选召回：基于岗位画像文本的向量相似度召回 Top N。
3. 精细评分：按技能、经验、项目相关性、岗位级别、行业经验和加分项计算分数。
4. 证据校验：每个正负结论必须关联简历原文；没有证据时标记为未知，不能推断。

最终分数由确定性规则基线和可选 LLM 评分组成。没有模型密钥时，规则基线仍可运行并接受测试。LLM 输出必须经过 JSON Schema/Pydantic 校验，失败时降级为规则结果。

### 7.5 Feedback

保存招聘人员对单条推荐的确认、驳回、改选岗位、原因标签和文字说明。反馈不直接在线改变权重，先进入离线评测集，避免不可审计的模型漂移。

### 7.6 Evaluation & Operations

负责固定数据集、匹配版本、Prompt 版本和指标计算。至少输出 Top-1 Accuracy、Top-3 Recall、硬性条件准确率、证据覆盖率、解析成功率、平均成本和分位延迟。

## 8. 数据模型

- `tenants`: 企业信息和状态。
- `users`: 企业用户、密码摘要、角色和状态。
- `job_templates`: 系统预置岗位模板。
- `jobs`: 企业岗位当前状态。
- `job_versions`: 不可变 JD 和结构化岗位画像。
- `resumes`: 候选人、处理状态、文件哈希和结构化画像。
- `resume_artifacts`: 原文件、提取文本和对象存储位置。
- `match_runs`: 一次匹配任务、算法版本、Prompt 版本和状态。
- `match_results`: 岗位版本、总分、维度分、结论、证据和排名。
- `feedback`: 人工确认、驳回、改选和原因。
- `model_traces`: 模型、Token、费用、时延、错误和关联业务对象。
- `audit_logs`: 登录、岗位变更、简历访问、删除和反馈操作。

结构化画像、维度分和证据使用 JSON 列保存；需要查询和约束的业务字段使用独立列。简历原文件不直接存入数据库。

## 9. API 边界

- `/api/v1/auth/*`: 登录、刷新和当前用户。
- `/api/v1/users/*`: 企业成员管理。
- `/api/v1/job-templates/*`: 预置模板查询。
- `/api/v1/jobs/*`: 岗位管理、版本、发布和停用。
- `/api/v1/resumes/*`: 上传、状态、详情和删除。
- `/api/v1/resumes/{id}/matches`: 发起匹配和查询结果。
- `/api/v1/match-results/{id}/feedback`: 提交或更新反馈。
- `/api/v1/analytics/*`: 质量、成本、延迟和失败样本。
- `/api/v1/health/live` 与 `/api/v1/health/ready`: 存活和就绪检查。

所有列表接口使用分页；所有写请求支持 request ID；异步操作返回任务状态而不是占用 HTTP 连接。

## 10. 错误处理与可靠性

- 文件上传限制扩展名、MIME、大小和解压后大小，文件名不参与物理存储路径。
- 解析和匹配任务具有 `queued/running/succeeded/failed` 状态、错误码和有限次数重试。
- 任务使用幂等键，避免重复上传或客户端重试产生重复匹配。
- LLM 调用设置超时、指数退避和熔断；失败后返回规则基线及明确的降级标记。
- 数据库写入使用事务；文件写入和数据库记录采用补偿清理。
- 删除简历采用软删除和审计记录，后台任务负责对象清理。
- 日志不记录简历正文、访问令牌或密码。

## 11. 安全、公平与合规边界

- 密码使用 Argon2 或 bcrypt 摘要，JWT 使用短期访问令牌和可撤销刷新令牌。
- 每个资源访问都执行租户和角色校验，使用集成测试覆盖 IDOR 场景。
- 敏感属性在进入匹配引擎前剔除。
- 结果页固定展示“仅供辅助评估，最终决定由招聘人员完成”。
- 审计日志记录谁在何时查看、删除、匹配或反馈了候选人数据。
- 提供候选人数据删除接口和保留期限配置。
- 防止简历正文中的 Prompt Injection 改写系统指令；文档内容只作为不可信数据传入。

## 12. 可观测性

- JSON 结构化日志包含 request ID、tenant ID、user ID、任务 ID 和业务对象 ID。
- Prometheus 指标覆盖请求量、错误率、分位延迟、任务积压、解析成功率和模型调用。
- 模型 trace 保存模型、Prompt 版本、输入输出摘要、Token、估算成本、延迟、重试和降级原因。
- 管理页面展示 Top-3 Recall、反馈接受率、解析失败率、平均费用和 P95 延迟。

## 13. 测试与验证

### 13.1 单元测试

- JD/简历结构校验、技能标准化、硬性条件、评分和证据覆盖。
- JWT、密码、角色策略、幂等键和状态机。

### 13.2 集成测试

- 登录、岗位版本、简历上传、匹配和反馈完整流程。
- 两个租户之间的列表、详情、修改、删除和匹配隔离。
- 任务重试、LLM 降级和对象存储失败补偿。

### 13.3 AI 回归测试

- 固定合成数据集并冻结测试集。
- 每次 Prompt、模型或评分权重变更都输出指标差异。
- CI 对硬性条件准确率和证据覆盖率设门槛；依赖外部模型的评测在受控作业中运行，普通 PR 使用确定性假模型。

### 13.4 性能验证

- 分别测量不含模型的 API 开销、文件解析吞吐和完整匹配时延。
- 使用 20 至 50 个并发用户的可重复压测脚本，报告测试环境和原始结果。

## 14. 前端页面

- 登录与企业空间。
- 招聘仪表盘：待处理简历、匹配任务、失败任务、反馈率和费用。
- 岗位模板与企业岗位管理。
- 简历上传、解析状态和结构化画像。
- 推荐结果：Top 3、雷达/条形维度分、满足项、缺失项、证据和反馈。
- 运营分析：质量、失败类型、成本和时延。

前端优先保证可解释性和操作闭环，不制作与招聘业务无关的聊天界面。

## 15. 分阶段交付

### 第 1 周：领域基础

完成数据库、迁移、租户、认证、RBAC、岗位模板、岗位版本和基础 UI/API。

### 第 2 周：简历管线

完成文件存储、异步任务、PDF/DOCX/TXT 提取、结构化画像、幂等与状态查询。

### 第 3 周：匹配与反馈

完成规则过滤、向量召回、精细评分、证据校验、Top 3 页面和反馈闭环。

### 第 4 周：评测与交付

完成合成数据、离线评测、可观测性、安全测试、CI、压测、Docker 部署、演示数据和简历材料。

## 16. 简历表述约束

简历只陈述可由代码、测试、评测输出或部署记录证明的事实。合成数据必须明确标注为合成数据；不得把演示环境称为真实生产环境，不得杜撰业务收入、用户量或可用性指标。
