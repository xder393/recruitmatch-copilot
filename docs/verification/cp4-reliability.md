## Physical smoke evidence and limits

An actual singleton Beat and an explicit test-image Fake Worker were launched in the isolated project with AI disabled, empty API key, deterministic512-dimensional embeddings and offline guards. Hard probes returned readiness200, both operational heartbeats were fresh and system overall was ok with AI deliberately disabled. After SIGKILL of only that synthetic Worker, readiness remained200 while system became degraded and Worker freshness expired; Beat remained fresh.

This was a physical Worker-heartbeat loss test, **not a controlled in-flight job termination test**. Separately, real PostgreSQL claims were explicitly expired and actual Beat recovered both Source types without a Worker, preserving attempt1/epoch1 and returning queued state. Seeded lease crash-state tests must not be described as physical in-flight recovery evidence. No real LLM/provider availability, BGE model download, large-load capacity, SLA, remote GitHub CI or production deployment was verified here.

Terminal successful AI-soft, permanent-failure and exhausted Sources are not automatically requeued merely to clear inactive staging. Explicit operator repair or privacy cleanup is required; safe current-owner reconciliation preserves historical/active/referenced generations. Recovery fairness is global oldest-effective-visit per bounded Source-type batch, not per-tenant service quotas. Worker count means recent main-process heartbeat observations, not execution capacity. Health timeout tests cover actual configured clients, not a universal DNS/OS latency guarantee. Enabled-but-unprobed AI is unknown/degraded; telemetry is explicitly not_configured until CP5.

## Controller decisions — chronological and exhaustive

The following15 rulings resolve plan/spec/interface ambiguities. Each retains the reason and cost if wrong; these are visible design tradeoffs, not hidden changes to the frozen business requirements.

This is a data-preserving additive upgrade, not another reset.

2. Ruling: keep each existing Source.status as the sole processing authority and translate legacy Knowledge uploaded/processing/ready to QUEUED/RUNNING/SUCCEEDED semantics; inactive is an existing non-claimable deactivation guard, never privacy deletion — frozen API stability and accepted ADR 0004 require retaining these public semantics while adding lease safety — cost if wrong: the adapter must maintain explicit status mapping rather than one shared literal enum; document and test both Source types, and do not add a second processing_status column. Existing error_code remains the one processing-error value; a synonym/typed port may expose processing_error_code without duplicating storage.

3. Ruling: strengthen the abbreviated Lease example to carry tenant plus source type/id and epoch, preserve active lifecycle and owned AVAILABLE Artifact checks, and keep renew/finalize/fail in caller-owned transactions via a minimal repository port/UoW composition — ID-only finalize and an independently committed guard would violate tenant isolation and allow stale side effects — cost if wrong: Task 1 legitimately also touches repository ports/UoW and defines a guarded ownership primitive for Task 2. No database/SDK imports in domain services. Expired ownership cannot be revived or used to finalize; compare time after acquiring the row lock, not a stale transaction-start timestamp.
